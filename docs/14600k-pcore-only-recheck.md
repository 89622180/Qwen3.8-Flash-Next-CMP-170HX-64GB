# i5-14600K 关掉小核之后：输出速度复测（2026-11-04）

机主把 PVE 主机的 BIOS 改成只开大核，反馈“输出速度变高”。本轮做了两件事：
**（1）在同机同臂上量化这件事的效果；（2）用可控实验判断 CPU 拓扑到底在不在关键路径上。**

## 1. 拓扑证据（都是读出来的，不是推断）

PVE 主机：

```
Model name:  Intel(R) Core(TM) i5-14600K      (dmidecode -s processor-version 同名)
CPU(s): 12   Thread(s) per core: 2   Core(s) per socket: 6   Socket(s): 1
/sys/devices/system/cpu/online : 0-11        offline : (空)
cpu0…cpu11 scaling_max_freq : 5300000        governor: powersave
```

14600K 是 6P + 8E = 20 线程；现在只剩 12 线程且 `thread(s) per core = 2`，即 6 个超线程大核、
小核已经从 ACPI 消失。主机开机时间约 00:18，PVE 自动快照 `auto-20261104-01212x` 是 01:20，
所以改动发生在今晚之前——**今天所有测量都是“纯大核”状态**。

CT103 内：`nproc = 12`、`online = 0-11`，引擎进程 `Cpus_allowed_list: 0,3-4,6,8,10`。

关键点：unit 里那行 `CPUAffinity=0 3 4 6 8 10`（作者原版就带着，10-13 起就在用）
**在小核还开着的时候就已经只圈大核了**。14600K 在 Linux 下 0–11 是 6 个物理大核的 12 个逻辑线程，
12–19 才是小核。也就是说“关小核”并不能把引擎挪到更大的核上——它本来就在那儿。

## 2. 与历史记录对比（跨天，口径相同）

0.32 臂，CT103，`bench_conc_text.py` 自然中文 2048-in / 256-out temp0 冷，配对 seed 1011/1012/1013：

| 指标 | 10-30（小核开） | 10-31 k=4（小核开） | **11-04（只有大核）** |
|---|---:|---:|---:|
| C1 单流 decode | 160.2 / 169.0 | 161.0 / 156.6 | 171.7 / 163.0 / 156.7 |
| C1 聚合 | 131.7 / 137.6 | — | 139.3 / 133.5 / 129.3 |
| C2 聚合 | 194.4 / 194.4 | 200.7 / 201.9 | 198.0 / 195.0 / 198.3 |
| C4 聚合 | 290.4 / 303.0 | 269.4 | 301.8 / 301.8 |
| C1 步频 steps/s | 45.9 | — | 45.1 / 46.4 / 46.5 |

**今天的数字落在历史区间之内，没有任何一格显著超出。** 最能说明问题的是步频：45.9 → 45–46.5，
每步调度开销没变——而 CPU 拓扑若真的影响这条臂，最先动的就是这个数。

诚实的限制：**做不到同日 A/B**。小核是 BIOS 项，要恢复得重启改回来，所以我只能给
“跨天对比 + 机制解释”，而仓库自己的规矩是跨天漂移 ~15 %（第 8.7 节），配置结论只认同日 A/B。

## 3. 机制实验：CPU 到底在不在关键路径上

跨天不可比，就做个当天可控的干扰实验：**交错**跑三种条件（每轮固定一个 seed，条件轮换，
先打 4 发 warm-up 把显卡时钟拉起来，避免“第一发慢是因为掉频”这种混淆）。

| 条件 | 干扰 | decode tok/s（seed 1011/1012/1013） | mean |
|---|---|---|---:|
| A idle | 无 | 170.7 / 167.0 / 165.4 | 167.7 |
| B | 6 个忙循环压在**没被圈**的 6 个线程（1 2 5 7 9 11） | 189.5 / 174.1 / 173.4 | 179.0 |
| C | 24 个忙循环压满 **0–11**（把圈住的 6 个也抢了） | 153.7 / 135.3 / 99.8 | 129.6 |
| D | 回到 idle 复测 | —（见结论） |

读法：

- B 相对 A **没有变慢**（甚至更高，在噪声内）：只要干扰不在被圈的那 6 个线程上，解码不受影响。
- C 明显变慢（−23 %，且逐轮恶化）：**解码只对“圈住的那几个大核被抢”敏感**。
- 结论：这条臂的 CPU 敏感度完全由 `CPUAffinity` 圈出的 6 个大核线程决定；小核从来不在集合里，
  关掉它们既不会把引擎推上更快的核，也不会少一份干扰。 measured 的“输出速度变高”
  **在这条臂上不成立**（更可能是跨天漂移，或客户端把 prefill 时间算进去了）。

注意这台机器上 CPU 侧的活并不轻：PLE 行缓存 4 GiB + 16 个 AIO worker + 预取窗口 262144，
`mpstat` 里能看到 `cpu3 %iowait 85`。也就是说**如果哪天 affinity 被改掉、或者主机后台
（ZFS/ARC、rsync、控制台轮询）挤进那 6 个线程，解码是真的会掉的**——这比小核的存在与否重要得多。

## 4. 顺手修掉的一个前置问题

CT103 的 `/models` bind 没了：今天 01:20 的自动快照流程（卸载模型 → 快照 → 加载模型）把
`mp0` 卸掉之后没挂回来，`pct config 103` 只在 `description` 里留着
`pve-model-mounts-v1: {"mp0":"/models,mp=/models,backup=0"}` 这条记账。
表现是 unit 的 `[Unit] ConditionPathExists=/models/…/model.safetensors.index.json` 静默拒绝启动。
本轮已 `pct set 103 -mp0 /models,mp=/models,backup=0` 恢复（与 CT120 一致）。
**结论：那对“卸载/加载模型”按钮之后要确认 mp0 回来了，否则下一次开机引擎不会起。**

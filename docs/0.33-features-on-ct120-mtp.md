# 第六轮：CT120（MTP 臂）复测 FLy 与 draft_lm_head（2026-11-04）

把卡从 CT103 倒到 CT120 跑的一轮。容器 `Qwen3.8F-MTP`，检查点同一个
（`Qwen3.8-Flash-Next-Uncensored-AutoRound-3bpw-MTP`，PLE/n-gram 95.37 GiB 走 SSD），引擎
**vLLM 0.33.0 + `ple-033` 臂**，草案是**原生 MTP k=4**（没有 DFlash2 的 candidate-head）。
CMP 170HX 64G（sm_80 = GA100 同核），功率上限 250 W 由机主自管。

## 0. 三条结论

1. **FLy 在 MTP 臂上的收益比 DFlash2 臂更大**：交错 A-B-A-B 三对、每臂一次真启动，
   解码中位数 **+15.1 % / +16.0 % / +29.9 %**，18 个配对 seed 里 fly 赢 16 个；
   池化两臂各 18 个 run：**162.9 vs 137.2 tok/s = +18.8 %**。prefill 与 KV 池零代价。
   代价还是那句：它**有损**（引擎 warning + 10 题里只有 3 题输出逐字节相同）。
2. **`draft_lm_head_quantization` 在这张卡上用不了**，但不是被 method gate 拒——MTP 臂过了 gate，
   死在权重加载阶段的 kernel 要求（原文见 §3）。
3. **更正第五轮的一处引用**：`--draft-lm-head-quantization` / `--enable-adaptive-verification`
   **在 0.33 里不是 CLI flag**，两个容器的启动日志都是 argparse 的 `unrecognized arguments`；
   第五轮文档里写成引擎的 gate 报错，那是我从源码拄的文案，不是日志给的。
   这两个字段只能走 `--speculative-config` JSON（`serve.sh` 现在提供了 `QWEN_DRAFT_LM_HEAD`）。

## 1. FLy：交错三对（decode，C=1，2048-in / 1024-out，seed 1011–1016）

| 对 | fly mean/median | 标准 mean/median | 中位差 | 逐 seed 配对胜负 | prefill fly/std |
|---|---|---|---:|---|---|
| AB1 | 162.1 / 157.0 | 127.9 / 136.3 | **+15.1 %** | 6/6 | 3359 / 3368 |
| AB2 | 166.9 / 161.8 | 144.4 / 139.5 | **+16.0 %** | 5/6 | 3341 / 3334 |
| AB3 | 171.4 / 175.1 | 144.1 / 134.8 | **+29.9 %** | 5/6 | 3334 / 3360 |
| 池化 | 166.8 / **162.9** | 138.8 / **137.2** | **+18.8 %** | 16/18 | — |

- 2048-token 输入的实际 prompt（pin）约 1289–1300，所以 prefill 那一列就是
  `docs/vllm-0.33-port-and-decode-sweep.md` §4 里“单 chunk 那一段”，两臂差 ≤0.8 % ⇒
  **FLy 不吃 prefill，也不吃 KV**：每次启动都是 `GPU KV cache size: 548,787 tokens / 2.09×`，
  `reserved 9.5 GiB … skipped memory profiling`（`QWEN_KV_BYTES` 钉池），`preempt=0` 全程。
- 接受长度：fly `3.23–4.42`（mean **3.739**），标准 `1.90–4.43`（mean **3.023**）⇒ +23.7 %，
  这就是收益的来源（fly 放宽了接受判据）。
- 两个负例都在 seed 1011：标准臂那一跑本身 acc_len 已经 4.267 / 4.433（4 个草案几乎全中），
  fly 没有可放宽的空间。**把两臂 acc_len ≥ 4.1 的 run 都剔掉再比**，差是
  +13.7 % / +17.8 % / +32.4 %，池化 **+18.7 %**——分层前后结论一致。
- 与第五轮 DFlash2 臂的 +9 % 不同量级，这条臂上 fly 更强；但那条“有损”的性质一样。
  `acc_len` 上限 = 1 + k = 5，本轮没有任何 run 进 acc_len ≥ 4.9 的循环吸引子，
  所以这组数字比第五轮那张表干净（第四/五轮的 ±20 % 判不出的问题在这里不存在）。

## 2. 质量：同一个 10 题探子，两臂各跑一次

`benchmarks/qa_lossy_check.sh`（temp 0、48 token、逐题 md5）：

| 臂 | 得分 | 逐字节相同的题 |
|---|---|---|
| 标准 | 8/10 | — |
| fly | 9/10 | **3/10**（第 2、4、5 题） |

fly 多对的一题是“水的化学式”：标准臂在 48 token 内只写到“用户问的是水的化学式…”就截断了，
fly 直接写 `水的化学式是 **H₂O**`——但那是下标 ₂，我的 ASCII 匹配器 `H2O` 判它 MISS，
所以这题的“对错”取决于探子而不是模型。**结论仍然是：分数没降不等于输出没变**，
10 题里 7 题的文本不一样（长度也从 5 B 到 271 B 各题都不同）。

## 3. `draft_lm_head_quantization`：过了 method gate，死在 kernel 要求

源码（`vllm/config/speculative.py`，0.33）：

```python
draft_lm_head_quantization: Literal["fp8", "nvfp4"] | None = None
...
if self.draft_lm_head_quantization is not None:
    if self.method not in ("eagle", "eagle3", "mtp") or self.use_gemma4_mtp():
        raise ValueError("draft_lm_head_quantization is not supported for method ...")
```

**它不是 CLI flag**（整棵树 `grep 'draft-lm-head'` 零命中），所以只能通过 speculative-config
JSON 进去；`serve.sh` 因此加了 `QWEN_DRAFT_LM_HEAD`，打出来的 argv 是

```
--speculative-config {"method":"mtp","num_speculative_tokens":4,"draft_lm_head_quantization":"fp8"}
```

启动日志：gate 放行（走到了 `load_draft_model`），2 min 41 s 后死在这里——

```
INFO [__init__.py:817] Selected MarlinFP8ScaledMMLinearKernel for Fp8PtpcOnlineLinearMethod
ValueError: FP8 PTPC online quant requires a kernel that honors per-token activation
quantization; MarlinFP8 is W8A16 weight-only. Requires SM89+ for Cutlass FP8 or
ROCm MI3xx for rowwise scaled_mm.
  File ".../model_executor/layers/quantization/online/fp8.py", line 419, in create_weights
  File ".../model_executor/layers/quantization/online/lm_head.py", line 105, in _quantize_copy
  File ".../v1/worker/gpu/spec_decode/mtp/speculator.py", line 20, in load_draft_model
```

机制上讲得通：FP8 PTPC 是 **per-token 激活量化**（W8A8），而 sm_80 没有 fp8 tensor core，
vLLM 在这张卡上只给得出 `MarlinFP8ScaledMMLinearKernel`（W8A16，权重-only），
不满足“honors per-token activation quantization”的契约，所以在建权重时主动拒绝。
`nvfp4` 那档更不用试（Blackwell 的 W4A16 路径）。
**判定：这条臂（以及这张卡）吃不到这个特性，不是配置问题。**

## 4. 这一轮顺带的两条日志事实

- `WARNING [arg_utils.py:2305] --mamba-cache-mode is deprecated and will be removed in v0.33.0.
  It has no effect: Mamba prefix caching follows --enable-prefix-caching.`
  —— 本臂一直传 `--mamba-cache-mode align`（serve.sh 里是硬编码），0.33 说它**无效果**。
  本轮没有改它：改这个 flag 会动 shipped argv，而第五轮的实测里 `--enable-mamba-shared-prefix-checkpoint`
  这类 mamba 相关开关都没给出提升，所以只记录，不动。
- `WARNING [speculative.py:1491] Enabling num_speculative_tokens > 1 will run multiple times of
  forward on same MTP layer, which may result in lower acceptance rate` —— MTP 每次启动都有；
  与 §1 里标准臂 acc_len 掉到 1.90–2.44 的那些 run 是同一件事的两面。

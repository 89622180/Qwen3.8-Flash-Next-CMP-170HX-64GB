# 第七轮：短上下文 prefill 的真正原因是 cudagraph 桶填充（2026-11-04，CT103）

第六轮那张 9 格 TTFT 表把 0.33 的 prefill 描述成“单 chunk 段掉 33 %、多 chunk 段反超”，
并把边界归到 `--max-num-batched-tokens 2048`。**那句边界是错的**：CT103 线上跑的是
`QWEN_BATCH_TOKENS=8192`（`systemctl show` 读到的 env，不是 serve.sh 的默认值），
所以 pin 332/654/1298/2592/5022 **全都是单 chunk**，chunk 数量根本不是一个变量。
真正的分界在别处，这一轮把它量出来了。

## 1. 机制：FULL cudagraph 的桶比请求大

线上 graph 配置（`/proc/<pid>/cmdline` 读到）：

```
"cudagraph_mode":"FULL_AND_PIECEWISE",
"cudagraph_capture_sizes":[1,…,32,64,128,256,512,1024,2048]     # max_cudagraph_capture_size = 2048
```

一个 M token 的 prefill 如果 ≤2048，就被**向上取整到最近的桶**再跑 FULL graph：

| pin tok | 落进哪个桶 | 白算的 slot | 浪费比例 |
|---|---|---:|---:|
| 332 | 512 | 180 | 35 % |
| 654 | 1024 | 370 | 36 % |
| **1298** | **2048** | **750** | **37 %** |
| 2592 | >2048 ⇒ 没有 FULL 桶，走 piecewise | 0 | 0 % |

0.32 走的是同一条桶规则（`CompilationConfig` 字段零变化），但它的 QSA 读的是 typed e5m2；
0.33 被迫换成 uint8 字节解码 e4m3（第六轮 §3），**每个白算的 slot 都变贵了**，
所以浪费比例相同的情况下 0.33 只在那个绝对浪费量最大的桶（1298 → 2048，750 slot）上被看出来。
这解释了为什么“凹陷”只在 1.3k 一格，而 2592 反而是赚的——2592 已经掉出 FULL 桶，没有白算。

## 2. 四臂实测（同会话、每臂一次真启动、每格 2 个不同 seed 取快的一遍）

| 臂 | capture sizes | pin 654 | **pin 1298** | pin 2592 | GPU KV 池 |
|---|---|---|---|---|---|
| BASE（本轮之前 shipped） | …,512,1024,2048 | 0.229 s / 2868 | **0.413 s / 3143** | 0.565 / 4637 | 553,415 tok / 2.11× |
| FINE（把桶加密） | …,512,768,**1280,1536,1792**,2048 | 0.196 / 3337 | 0.374 / 3471 | 0.561 / 4620 | 551,334 / 2.10× |
| SHRUNK（砍掉 2048 桶） | …,512,1024 | 0.228 / 2868 | 0.365 / 3556 | 0.560 / 4629 | **570,059 / 2.17×** |
| **COMB（加密 + 砍顶桶）= 现在 shipped** | …,512,**768,1024** | **0.194 / 3371** | **0.366 / 3546** | 0.565 / 4629 | **570,059 / 2.17×** |
| 0.32 对照（第六轮 §4） | …,512,1024,2048 | 0.224 / 2897 | 0.326 / 3982 | 0.677 / 3804 | 557,576 / 2.13× |

COMB 上线后再测一遍（同一引擎、shipped 状态）：332 → 0.131 s / 2534，654 → 0.191 / 3424，
1298 → 0.363 / 3576，2592 → 0.560 / 4629，`preempt=0`，0 条 error。

**结果**：
- 1298 那格的 TTFT 从 0.413 s 降到 0.363 s，**拿回 50 ms**（+87 ms 的回退缩到 +37 ms，
  恢复 57 %），prefill 3143 → 3576 tok/s（+13.8 %）。
- 654 那格从 0.229 降到 0.191，**反超 0.32 的 0.224**（+15 %）。
- 332 那格 0.131，与 0.32 的 0.132 打平。
- 2592 / 5022 不动（它们本来就不在 FULL 桶里），0.33 在那两格仍然领先 17 % / 3 %。
- **KV 池白赚 16,644 tokens**（553,415 → 570,059，2.11× → 2.17×），因为少捕一张 2048 的
  FULL graph 就少占一块显存。

## 3. 剩下那 20–40 ms 是什么

桶填充解释完了之后，1298 还比 0.32 慢 20–40 ms（这一格现在三次独立启动给 0.348 / 0.363 / 0.366，
0.32 是 0.326）。这一格和 2592 现在走的是同一条 piecewise 路，而 2592 上 0.33 **领先** 0.32
（0.560 vs 0.677），所以剩下的差异不是“路径慢”，而是**这个尺寸下 e4m3 字节解码 kernel 本身**
（第六轮 §3 那条被强制换掉的数值路径）。

为了确认这一点，在新桶上把 `Q38_SM80_FP8_TILES` 又重跑三档（每档一次真启动，同 2 seed 取快的一遍）：

| tile | pin 332 | pin 654 | **pin 1298** | pin 2592 | KV 池 |
|---|---|---|---|---|---|
| `table`（关掉 sm_80 覆盖） | 0.136 / 2441 | 0.194 / 3371 | 0.368 / 3527 | 0.571 / 4539 | 570,059 / 2.17× |
| **`128,4`（上游默认 = shipped）** | 0.136 / 2441 | 0.189 / 3460 | **0.348 / 3730** | 0.571 / 4539 | 570,059 / 2.17× |
| `64,8` | 0.135 / 2459 | 0.195 / 3354 | 0.376 / 3452 | 0.600 / 4320 | 570,059 / 2.17× |

默认那档仍是最快的，`64,8` 全面更差 ⇒ **tile 不动，不设 env**（与上游一致）。
所以剩下的 20–40 ms 归到数值路径本身，不是还能调的 flag；要再拿就得改 kernel。

- CT103：新 drop-in `/etc/systemd/system/qwen38-032-test.service.d/zz-finegraphs.conf`
  （仓库副本 `configs/ct103-0.33-finegraphs.conf`）
  ```ini

  ```
  只改一个 env，不动 `serve.sh`、不动 venv、不动权重。回滚 = 删这个文件 + `daemon-reload` + `restart`。
- **CT120 没有被改动**。它的 1.3k 格（MTP 臂，pin 1289 时约 3350 tok/s）机制同源，但这套桶
  在那条臂上**没实测过**，所以只把文件留在仓库里：要试就把同一个 drop-in 拷到
  `/etc/systemd/system/qwen38-032-test.service.d/zz-finegraphs.conf`（CT120 也是这个 unit 名），
  daemon-reload + restart，然后按 §2 的三格对照量一遍。
- 为什么砍掉 2048 桶不伤 decode：decode 每步的 token 数是 `seqs × (1+k)`，本臂最多 8×5 = 40，
  远在小桶范围内；2048 桶只服务 prefill 与混合批 ≤2048 的情况，而那正是我们不想再用 FULL graph 的区间。
  实测也印证了：新桶上线后 decode C1 三个 seed 给 163.3 / 164.4 / 185.6（与 shipped 前的 159–164 同档），
  `spec_decode` 计数 640 drafts / 1251 accepted ⇒ acc_len 2.955 正常，`preempt=0`。
